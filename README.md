# doc-photo-qa

## Запуск

```bash
docker compose up
```

Сервис: `http://localhost:5000`, Swagger: `http://localhost:5000/docs`.

```bash
curl -F "file=@photo.jpg" http://localhost:5000/api/check
```

## API

`POST /api/check`, поле `file` (JPG или PNG, до 10 МБ).

```json
{
  "ok": false,
  "reasons": [{"code": "BLURRY", "message": "Фото размыто. Держите телефон неподвижно и дождитесь фокусировки."}],
  "scores": {
    "document": {"corner_score": 1.0, "fallback_score": null, "text_boxes": 14, "flat_share": 0.07},
    "framing": {"edge_margin": 0.10, "fallback_sees_corners": null},
    "geometry": {"area_share": 0.41, "side_ratio": 1.05, "max_angle_dev": 3.1},
    "quality": {"sharpness": 9.4, "brightness": {"mean": 161.0, "dark_share": 0.0, "bright_share": 0.0}, "glare_share": 0.0}
  }
}
```

Повреждённый файл или другой формат: HTTP 415 (`INVALID_IMAGE`). Файл больше 10 МБ или больше 60 Мп: HTTP 413. Ответ в том же формате, `scores: null`. `GET /api/health` возвращает `{"msg": "OK"}`.

## Проверки

Сначала находим документ, затем все остальные проверки работают по его углам. Запускаются все проверки, чтобы вернуть все причины сразу.

| # | Проверка | Коды | Подход |
|---|---|---|---|
| 1 | Есть документ | `NO_DOCUMENT`, `SCREENSHOT`, `BLANK_PAGE` | DocCornerNet даёт 4 угла и вероятность документа. Если документ мелкий и основная модель его не видит, запускаем DocAligner. Скриншот: доля идеально ровных блоков 8x8 (у камеры всегда есть шум). Пустой лист: PP-OCR находит 0 текстовых областей на выпрямленном документе |
| 2 | Документ целиком | `DOCUMENT_CUT` | Угол ближе 3% к краю кадра считается подозрительным, тогда вторая модель решает: если она уверенно видит все 4 угла, документ не обрезан |
| 3 | Размер и угол | `TOO_SMALL`, `TOO_TILTED` | Доля площади документа в кадре; перспектива по отношению противоположных сторон и углам четырёхугольника |
| 4 | Резкость | `BLURRY` | Дисперсия второй производной по 4 направлениям, берём минимум (ловит смаз в одну сторону). Документ приводим к 384 px и слегка сглаживаем, чтобы шум сенсора не выглядел как резкость |
| 5 | Освещение | `TOO_DARK`, `OVEREXPOSED`, `GLARE` | Яркость и доля чёрных/белых пикселей внутри документа. Блик: яркие бесцветные пятна заметно ярче самой бумаги |

## Модели

Все работают на CPU через onnxruntime, лицензии открытые.

| Модель | Зачем | Лицензия |
|---|---|---|
| [DocCornerNet LEAN](https://github.com/mapo80/DocCornerNet-CoordClass) | основной детектор углов | MIT |
| [DocAligner lcnet100](https://github.com/DocsaidLab/DocAligner) | мелкие документы и проверка обрезки | Apache-2.0 |
| PP-OCRv4 det (PaddleOCR, ONNX из `rapidocr-onnxruntime`) | только находит текст, не читает | Apache-2.0 |

Почему они: сравнивал детекторы углов на датасете и своих фото. DocAligner точнее на датасете, но на реальных фото (белая бумага на светлом столе) DocCornerNet нашёл 11 из 13 документов против 6 у DocAligner и работает в 4-5 раз быстрее (около 12 мс). Классический OpenCV (Canny + контуры) находил только половину документов. CLIP zero-shot для «это документ?» оказался нестабильным, поэтому отказался от него в пользу детектора текста.

## Оценка качества

```bash
pip install -r eval/requirements.txt
docker compose up -d
python eval/evaluate.py
```

Набор уже лежит в репозитории: `data/test_set/images` и разметка `data/test_set/labels.csv` (колонки `file, ok, reasons, source, kind`). Пересобрать его можно командой `python eval/build_dataset.py`, результат побайтово тот же.

**Набор (169 фото: 49 хороших, 120 плохих).** Документы реальных людей не используются:
- `data/source`: кадры MIDV-500/2019 (образцы документов) и SmartDoc из [DocCornerDataset](https://huggingface.co/datasets/mapo80/DocCornerDataset) с эталонными углами.
- `data/own`: свои фото без персональных данных;
- искусственные дефекты с фиксированным seed: обрезка, перспектива, размытие и смаз с шумом, затемнение, пересвет, блик, пустой лист, скриншоты. Обрезка и перспектива строятся по эталонным углам датасета, а не по нашему детектору.

Хорошие кадры и реальные плохие (размытые, с бликом) отобраны вручную, список в `eval/selection.json`. 

**Результаты** (Docker, AMD Ryzen 5 5600H):

| | |
|---|---|
| хорошие фото отклонены | 8.2% (4 из 49) |
| плохие фото пропущены | 5.0% (6 из 120) |
| время ответа | среднее 315 мс, максимум 582 мс |

| Проверка | Точность | Полнота |
|---|---|---|
| документ | 89% | 100% |
| целиком в кадре | 81% | 87% |
| размер и угол | 86% | 86% |
| резкость | 63% | 91% |
| освещение | 82% | 76% |

Модели загружаются и прогреваются при старте, поэтому первый запрос тоже быстрый.

## Как подбирал пороги

Пороги качества подбирал на отдельной калибровочной выборке (711 фото): 33 чистых документа и их копии с дефектами разной силы. Слабые дефекты (лёгкое размытие, JPEG, шум, затемнение) размечены как хорошие, чтобы мерить ложные отказы. Для каждой проверки перебирал порог и брал тот, где полнота максимальна при ложных отказах на чистых фото около 2% (для блика около 4%: точнее разделить не удалось). Геометрию и обрезку проверял на кадрах с эталонными углами. Главный приоритет: хорошие фото должны отклоняться редко.

## Где сервис ошибается

- **Блики на ламинированных удостоверениях.** Естественные отблески ламината похожи на настоящие блики. Полнота по `GLARE` 46%, и 2 из 4 ложных отказов из-за этого.
- **Фото экрана телефона или монитора.** Это обычное фото с камеры, поэтому проверка скриншотов его не ловит.
- **Несколько причин на одном фото.** Реальные кадры с бликом часто ещё и размыты; разметка указывает только главную причину, поэтому часть «лишних» `BLURRY` на самом деле верна.
- **Слабое размытие на крупных документах.** Резкость меряется относительно размера документа, поэтому лёгкая расфокусировка крупного документа может пройти.
- **Наклон мелкого документа.** Перспектива почти не меняет форму маленького документа, поэтому сильный наклон ловится только когда документ крупный (полнота `TOO_TILTED` 70%).

## Что бы сделал иначе

- Собрал бы больше своих реальных фото с дефектами вместо синтетики, особенно блики и фото экранов.
- Обучил бы лёгкий классификатор (например, на эмбеддингах CLIP) для скриншотов и фото экрана.
- Блик определял бы по сравнению с локальной яркостью бумаги и учитывал бы, закрывает ли он текст.
- Для резкости мерил бы чёткость только на найденных текстовых областях.

## Структура

```
run.py, settings.py     запуск и все настройки
app/
  api.py                /api/check и /api/health
  image_io.py           безопасное чтение изображения
  document.py           модели, проверка 1
  framing.py            проверка 2
  geometry.py           проверка 3
  quality.py            проверки 4 и 5
  messages.py           коды причин и тексты
  schemas/              pydantic-схемы ответа
models/                 ONNX-модели
eval/                   сборка набора и оценка
data/test_set/          тестовый набор с разметкой
data/source/            исходные кадры датасета и их эталонные углы
data/own/               свои фото без персональных данных
```
